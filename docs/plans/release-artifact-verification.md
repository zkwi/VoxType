# 安装包来源验证设计

对应 issue #34。本文只做设计，不含实现；实现按结论分阶段另开改动。

## 现状

`src-tauri/src/update.rs` 的更新链路：

1. 向 `https://api.github.com/repos/{repo}/releases/latest` 请求最新 Release。
2. 用 `installer_score` 按资产名挑选 Windows 安装包。
3. 通过 HTTPS 下载到 `%TEMP%\VoxType-update\` 下的同名资产。
4. 以 `/S /R` 静默启动该可执行文件。

现有保护只有传输层：reqwest 走 rustls 做证书校验，仓库名来自本地配置。**下载完成到执行之间没有任何完整性或来源校验**。另外 GitHub API 返回的 `asset.size` 已经被读取并记录进日志，但从未与实际下载到的字节数比对。

## 威胁模型

按攻击者能力分层，明确每层现状与目标：

| 层级 | 攻击者能力 | 现状 | 目标 |
| --- | --- | --- | --- |
| T1 传输损坏 | 网络中断、代理截断、缓存返回不完整内容 | 无检测，可能执行截断文件 | 必须检测并中止 |
| T2 中间人篡改 | 篡改 HTTPS 流量 | 已由 rustls 证书校验阻断 | 维持 |
| T3 发布资产被替换 | 攻破维护者 GitHub 账号或具备仓库写权限，替换 Release 资产 | 无防护，恶意安装包会被静默执行 | 必须阻断 |
| T4 构建链投毒 | 攻破维护者本机构建环境 | 无防护 | 超出本轮范围，记录为已知残余风险 |

T3 是本设计的核心。它同时决定了信任锚不能只放在同一个 GitHub Release 里——攻击者若能替换安装包，同样能替换与之并列的摘要文件。

## 候选信任锚

### A. Authenticode 代码签名

优点：Windows 原生信任，顺带缓解 SmartScreen 警告。

缺点：证书需持续付费，EV 证书还涉及硬件令牌；对个人项目而言成本与密钥管理负担最重。不作为首选。

### B. 发布摘要文件

在 Release 中追加 `安装包名.sha256`，应用下载后比对。

能挡住 T1，**挡不住 T3**：摘要与安装包同源，攻击者可同时替换两者。只能作为第一步，不能声称解决了来源可信问题。

### C. minisign 风格的分离签名（推荐）

维护者离线持有私钥，发布时对安装包生成分离签名文件；**公钥编译进应用**。应用下载安装包与签名后用内置公钥校验。

- 能挡住 T3：攻击者拿不到私钥就无法伪造签名，替换资产会导致校验失败。
- 信任锚在应用二进制里，不在 Release 里，来源独立。
- Tauri 官方 updater 采用同一思路，方案成熟。
- 负担：一把需要长期保管的私钥，发布时多一步签名。

### D. GitHub 构建来源证明（Sigstore attestation）

`actions/attest-build-provenance` 生成可验证的构建来源证明，无需自管密钥。

前提是**发布构建必须在 GitHub Actions 中进行**。当前发布包是在维护者本机 `npx tauri build` 产出的，CI 只做 debug 构建。改造成本较高，且会把构建环境的信任转移给 CI。列为可选的后续阶段。

## 结论与分阶段计划

### 阶段一：长度与摘要校验（低成本，先做）

- 发布侧：在现有发布流程中生成 `安装包名.sha256` 并作为 Release 资产上传。发布说明中已经记录 SHA-256，改为由脚本生成同一份值，避免手抄。
- 应用侧：下载后先比对 `asset.size` 与实际字节数，再计算 SHA-256 与摘要文件比对。任一不符即中止，不落地可执行文件。
- 明确边界：该阶段只解决 T1。文档与发布说明**不得**把它表述为"验证了来源"。

### 阶段二：分离签名（真正的信任锚）

- 维护者本机离线生成密钥对，私钥存放在仓库和 CI 之外，永不进入版本库或 Actions secrets。
- 公钥同时提交进仓库并编译进应用；README 与 SECURITY.md 公示公钥指纹，便于第三方独立核对。
- 发布侧：对安装包签名，签名文件作为 Release 资产上传。
- 应用侧：下载安装包与签名，用内置公钥校验通过后才允许执行。
- 该阶段落地后，阶段一的摘要校验保留为廉价的前置快速失败。

### 阶段三（可选）：构建来源证明

仅当发布构建迁移到 GitHub Actions 后再评估。届时可叠加 attestation，为第三方提供不依赖维护者私钥的独立验证路径。

## 失败处理与用户体验

- **失败即中止，绝不降级放行。** 校验失败时不启动安装程序，并立即删除已下载文件。
- 错误码与现有网络错误区分开，便于日志定位；用户提示需说明：发生了什么、可能原因（下载损坏或资产被改动）、下一步怎么做（前往 Release 页面手动下载并自行核对 SHA-256）。
- 提示中不暴露临时目录完整路径（含用户名），沿用现有脱敏口径。
- 应用内更新失败不得影响正在进行的录音或已完成的文本输出。

## 向后兼容

- 阶段二上线前发布的历史 Release 没有签名。应用只会安装**更新的**版本，因此不需要为历史版本放行例外。
- 一旦应用要求签名，缺少签名资产的 Release 一律失败关闭，并引导用户手动下载。这意味着发布流程必须先稳定产出签名，再发布带强校验的应用版本，顺序不能颠倒。
- 建议的上线顺序：先发布一版同时产出签名资产但仅告警不拦截的应用；确认签名流程稳定后，再发布强制校验的版本。

## 密钥管理与轮换

- 私钥离线生成，至少两份离线备份，永不进入仓库、CI 或云同步目录。
- 公钥指纹公示在 README 与 SECURITY.md，变更须在发布说明中显著标注。
- 轮换：先发布一版同时信任旧公钥与新公钥的应用，待多数用户升级后再停用旧公钥。
- 私钥疑似泄露时：立即轮换、作废受影响版本的信任、按 SECURITY.md 的私有渠道发布说明。

## 实现阶段的回归计划

实现时需覆盖的测试：

- 摘要匹配与不匹配各一条，不匹配必须返回中止错误且不产生可执行文件。
- 下载字节数与 `asset.size` 不一致时中止。
- 签名有效、签名无效、签名资产缺失三种情况。
- 公钥轮换期间新旧签名都可通过。
- 错误码与现有网络错误、HTTP 状态错误互不混淆。
- 校验失败后临时文件已被清理。

## 手工验证清单

1. 正常发布：应用内更新能完成，日志记录校验通过。
2. 人为篡改本地已下载的安装包一个字节：校验失败，安装不启动，文件被清理，提示可读。
3. 移除 Release 中的签名资产：更新失败并引导手动下载。
4. 用错误的私钥签名：校验失败。
5. 安装包与签名均正确但版本号低于当前：沿用既有"已是最新"逻辑，不进入下载。

## 残余风险

- T4 构建链投毒不在本设计范围内。若维护者本机在构建时已被攻破，签名会为恶意产物背书。缓解方向是阶段三的 CI 构建加来源证明。
- 未做 Authenticode 签名，Windows SmartScreen 仍会对安装包告警。这一点在 README 和发布说明中已有说明，本设计不改变该现状。

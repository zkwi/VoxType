# VoxType 0.13.0 输入延迟优化与豆包 API Key 接入发布审计

日期：2026-09-16

## 版本判断

本次从 `0.12.1` 升到 `0.13.0`。改动包含用户可见的新接入方式（豆包语音控制台 API Key）、设置界面与配置模板调整，以及主链路上可实测的输入延迟改进，属于新功能加默认策略调整；不破坏旧配置，按项目版本策略升 minor。

## 用户问题与实现结论

用户问题是"语音输入体感慢"，具体分成首字上屏速度和最终润色后粘贴速度两段，并要求评估更换模型与模型参数。排查结论是两条链路当时都处于不可用或次优状态：

- 豆包侧 `mode = "agent_plan"` 的密钥打方舟端点返回 `45000000 InvalidSubscription`，方舟订阅已失效，识别整条链路不可用；旧 `app_key`/`access_key` 实测仍可用。
- 润色侧安装版配置的 `qwen3.8-max` 返回 `403 AccessDenied.Unpurchased`，润色一直静默失败回退原文。

对应处理：

- 新增第三种豆包接入方式 `auth.mode = "api_key"`，对应新版语音控制台「API Key 管理」创建的密钥，走 `[request].ws_url` 指定的标准端点，发送 `X-Api-Key`、`X-Api-Resource-Id`、`X-Api-Request-Id` 和 `X-Api-Connect-Id`。实测该密钥打方舟专属端点返回 401，两种方式的密钥不通用，因此必须作为独立模式而不是复用 `agent_plan`。
- 延迟优化落在本地链路，不改变服务端识别参数。

## 参数与模型选型依据

用 13.2s 音频样本在标准端点 `bigmodel_async` 上逐项实测（明细见 `docs/asr-quality-latency-guardrails.md`）：

- 尾部积压补发速度是最终延迟的最大单项，值 1-2 秒，因此本次只改这一项。
- `end_window_size` 由 800 改 400 对最终延迟没有可观测收益：发出负包后服务端立即收尾，不等 VAD 窗口，维持默认 800。
- `enable_accelerate_text` + `accelerate_score=10` 实测首字没有加快，维持默认关闭。
- `enable_nonstream=false` 只省约 350ms 却放弃二遍识别准确率，维持默认开启。
- 服务端在最终包之后立即关闭连接，1.2s 内不再补包，本地 300ms settle 几乎不触发，不调整。

润色模型在同一套系统提示词和参考信息下对比（各 3 次取中位数）：短句 50 字 `mimo-v2.5-pro` 2613ms、`deepseek-flash` 757ms、`deepseek-v4-pro` 836ms；长段 190 字分别为 3376ms、895ms、1335ms。DeepSeek 上下文缓存命中 1209 token 中的 1024，精简系统提示词只再省约 200ms，因此保留完整提示词不牺牲润色质量。模型与密钥属于用户本地配置，不随版本分发。

## 主链路影响

- 发包节奏：新增 `SendPace`，队列积压 ≥2 包时按 `100ms` 补发，音频输入关闭后的尾部积压按 `50ms` 清空，其余情况仍按分片时长发送。音频分片保持 `200ms`，实时说话阶段节奏不变，仍在豆包建议的 `100-200ms` 区间内。
- 建连顺序：WebSocket 握手与屏幕 OCR 等待并行，握手不依赖 OCR，只有首包 payload 依赖；OCR 结果解析一次后由 ASR 首包和 LLM 润色共用，语义与改动前一致。
- 录音启动顺序：屏幕 OCR 改在麦克风启动和系统静音之前发起。OCR 本来就在独立线程执行，提前发起不占用录音启动时间；麦克风启动失败时这次 OCR 结果被直接丢弃。
- 最终包门禁、`definite=true` 分句选择、空识别失败态、停录尾音窗口、剪贴板失败兜底和恢复原剪贴板策略均未修改。
- 阿里云 FunASR 通道仍在建连前解析 OCR 上下文，行为与改动前一致。

## 配置、界面与文档

- `auth.mode` 新增允许值 `api_key`；保存校验只对 `agent_plan` 保留固定 Resource ID 约束，`api_key` 模式沿用用户配置的 Resource ID（小时版为默认）。
- 新增配置字段 `auth.console_api_key` 存放语音控制台密钥，`auth.api_key` 保持"方舟 Agent Plan 专属密钥"的原语义。三套凭据各有独立字段，切换接入方式不会互相覆盖；已发布版本里 `api_key` 只可能是 Agent Plan 密钥，因此不需要迁移逻辑。
- 默认值按来源拆开：`AppConfig::default()`（全新安装、尚无配置文件）用 `api_key`，与配置模板、设置页下拉首项和 README 示例一致；serde 的缺字段默认仍是 `app_access`，保证早于该字段的手写配置行为不变。两条路径各有回归测试。
- `auth.resource_id` 为空串时在加载阶段补回默认小时版资源。设置页没有该字段入口，此前手工留空会让首页提示"未配置"但用户无处可改。
- `config.example.toml` 注释同时说明新建默认与缺字段回退两种情况。
- 设置页新增接入方式选项与密钥输入框，帮助文档按当前模式跳转；三语言文案同步新增 `doubaoAuthModeApiKey`、`doubaoConsoleApiKey`、`doubaoConsoleApiKeyHint`，并更新接入方式说明文案。
- 同步更新 README、README.en、Setup Guide 中英文、Feature Guide 中英文、Troubleshooting 中英文、ASR 守门清单、配置模板与 CHANGELOG。

## 右 Alt 触发独占按键

发布过程中用户反馈：Chrome 表单里按右 Alt 或鼠标中键会失焦，Ctrl + Q 不会。

定位结论是三种触发走三条不同通道。Ctrl + Q 用 `RegisterHotKey`，系统在分发前吃掉，前台程序收不到。鼠标中键走低层鼠标钩子，启用时已经 `return LRESULT(1)` 拦下，未启用才会漏给 Chrome 触发自动滚动。右 Alt 走低层键盘钩子但固定放行，Chrome 按 Windows 惯例把孤立 Alt 当作激活菜单栏，于是失焦。

用户要求改成"和 Ctrl + Q 一样用全局热键注册"。实测这条路走不通：`RegisterHotKey` 对 `VK_MBUTTON` 和 `VK_RMENU` 都返回注册成功，但注入 3 次右 Alt 收到 0 次 `WM_HOTKEY`，同一套注入与消息回收在对照组 `Ctrl+Shift+F9` 上收到 1 次，证明注入有效而右 Alt 确实不触发——Windows 的热键匹配发生在非修饰键的按下上，鼠标输入也不走键盘热键路径。此外 `RegisterHotKey` 的修饰位只有 `MOD_ALT`，无法区分左右 Alt。

改为在键盘钩子里做与鼠标中键一致的拦截：启用右 Alt 触发时按下和松开都返回 `LRESULT(1)`。只拦松开会让前台程序只收到按下、等不到松开，留下修饰键卡死状态，比原状况更糟。注入事件仍然放行，VoxType 自己模拟的粘贴按键不受影响；未启用时行为完全不变。

代价已写入三语言界面文案、README 中英文、Feature Guide 中英文和 Troubleshooting 中英文：开启期间右 Alt 组合键失效、AltGr 布局受影响，左 Alt 不受影响，关闭触发即恢复。默认仍为关闭，未触碰"右 Alt 与鼠标中键默认关闭"这条不可回退策略。

决策逻辑抽成 `right_alt_hook_action`，覆盖启用/未启用 × 按下/松开 × 注入/非注入 × 其他按键四组回归测试。端到端无法由 AI 自测：钩子按设计忽略 injected 事件，而任何程序化按键都会被标为 injected，需要真实物理按键。

维护者已在安装版 `0.13.1` 上手工验证通过：开启右 Alt 触发时，浏览器表单中按右 Alt 不再丢失焦点；关闭该触发方式后恢复为原有行为。

## PR 自动化评审

合并前 GitHub 上的自动化评审（Codex）提了一条 P2：两种 API Key 接入方式在设置页都绑定到 `config.auth.api_key`，切换模式会复用、覆盖另一种方式的密钥，与本次发布文档"几套凭据独立保存"的说法矛盾；而这两种密钥恰恰不通用，填错会 401。

复核确认属实，且是本轮引入的问题：0.11.0 建立的设计口径就是"两套凭据独立保存，切换后只使用当前方式"，新增第三种方式时复用同一字段破坏了这条口径。已按新增独立字段修复，并补了 Rust 与前端各一条"切换模式不丢另一套密钥"的回归测试。因为 0.13.0 尚未发布，已发布配置中 `api_key` 只可能是 Agent Plan 密钥，所以不需要迁移代码。

## 工具链差异

首次推送后 CI 的 clippy 失败，本地 `npm run ai:release-check` 却通过：CI 用 `dtolnay/rust-toolchain@stable` 取最新 stable，本机是 rustc/clippy 1.95，新增的 `clippy::chunks_exact_to_as_chunks` 只在前者存在。命中的是 `audio.rs` 两处既有代码，与本轮改动无关，已按建议改写为 `as_chunks`。后续可考虑加 `rust-toolchain.toml` 固定工具链，让本地检查和 CI 结论一致。

## 已知差异与后续项

- 屏幕 OCR 在 4K 全屏下耗时 412-812ms，仍可能超过 500ms 等待上限被跳过。本次通过提前发起 OCR 缓解，未改动截图分辨率：降采样会同时降低界面小字的识别率，需要单独的质量样本评估，留作后续项。
- 迟到的 OCR 结果目前不会被 LLM 润色阶段二次取用。可在不增加任何等待的前提下补齐，但会给主链路引入额外并发状态，本次发布不做。
- 仓库开发版配置 `enable_ddc = false` 与守门清单记录的默认开启不一致，属于用户本地取舍，本次不代为修改。

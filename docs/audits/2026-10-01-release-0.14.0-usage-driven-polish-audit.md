# VoxType 0.14.0 基于真实使用的精修与工程治理发布审计

日期：2026-10-01

## 版本判断

本次从 `0.13.1` 升到 `0.14.0`。改动包含用户可见的行为变化（开机自启动静默待在托盘、操作提示改写、首页卡片精简）、主链路上的稳健性修复（剪贴板独占打开、日志原子写入）、可实测的资源占用下降，以及两个无效配置项的移除；不破坏旧配置，按项目版本策略升 minor。

## 用户问题与本轮范围

用户要求基于实际使用情况和最近日志，对项目做一次完整的设计优化与精修，范围覆盖体验、速度、代码质量和工程治理（文档、分支、依赖），并发布新版本、更新本机运行的版本。

本轮不是围绕单一需求，而是先看数据再定清单。因此把“看过、量过、决定不改”的结论也一并记录，避免以后重复排查。

## 已验证并修复的问题

### 剪贴板读回校验失败

最近 15 天 1608 次成功输出里有 145 次（9%）在写入剪贴板后读回失败，错误固定为 `Thread does not have a clipboard open (0x8007058A)`；按天分布极不均匀，多数日子为 0，个别日子达到 57/79（72%）。

根因是 `OpenClipboard(NULL)` 不独占。用一段探针在本机复现：线程 A 以 NULL 打开剪贴板后，线程 B 再以 NULL 打开仍然成功，随后线程 A 读取即报上面的错误，与日志逐字一致。写入后立刻读回时最容易撞上，因为监听剪贴板的程序正好在这时来读刚写入的内容。按天聚集的分布也与“某个监听程序当天是否在运行”吻合；具体是哪个程序属于推断，未做确认。

改为用本线程的隐藏消息窗口打开后，同一探针里线程 B 的打开被拒绝，线程 A 读取正常。冲突改为表现成可重试的“拒绝访问”，先做 5 次 5ms 短重试，再走按配置的慢速重试。

此前的实际影响限于跳过校验和每次两条告警，文本仍能正常粘贴；但同样的夺取也可能发生在快照读取中途，届时会表现为原剪贴板部分格式丢失，所以按根因修复而不是只压掉告警。

### “部分格式未备份”误报

最近 15 天 446 次（28%）输出带有这条提示。其快照大小集中在 4-8MB，是剪贴板里放着截图的典型形态：`CF_DIB` 已按内存备份，句柄型的 `CF_BITMAP` 无法备份而被计为丢失。实际上恢复 `CF_DIB` 后系统会重新合成 `CF_BITMAP`，手工回归测试在真实剪贴板上确认了这一点。

现在快照记录每个未备份格式的编号，系统可从已备份格式重新合成的不计入丢失：位图族只要备份了 DIB 就互相合成；文本族只认“已备份 Unicode 文本”这一个方向，从 ANSI 文本反推 Unicode 会丢字符，仍按丢失计。额度用完后继续枚举剩余格式的编号但不再读取数据，才能做这个判断。该提示本来就不展示给用户，日志级别同步从告警降为 info，并去掉重复的第二条。

### 日志行互相穿插

四个日志文件里有 18 行是两条日志的字节互相穿插。原因是每行被拆成多次写入且没有互斥。改为整行格式化后一次写入，轮转与追加在进程内串行；日志路径只解析一次。

时间戳同步改为毫秒精度。本次分析里阶段耗时只能靠大量样本取均值，正是因为秒级时间戳无法区分 300ms 和 900ms。

### 窗口隐藏时的占用

对已安装的 0.13.1 采样：

| 场景 | 占用（单核百分比） | 主要来源 |
| --- | --- | --- |
| 空闲，两个窗口都隐藏 | 合计约 2.7% | 主进程 1.2%，WebView 浏览器进程 0.7%，字幕窗渲染进程 0.3% |
| 录音中，主窗口隐藏 | 合计约 33% | GPU 进程 17%，主窗口渲染进程 12% |

空闲占用来自字幕窗页面：不论是否显示都每 250ms 调一次 `get_overlay_text`、每秒调一次 `get_overlay_config`，后者每次都重新读取并解析配置文件。现在隐藏时降为 2 秒心跳且不读配置；显示前后端推送的事件会立刻恢复 250ms。保留心跳而不是完全依赖事件，是为了在事件丢失的假想情况下最多 2 秒也能恢复，代价是每 2 秒一次很轻的调用。

录音期间主窗口渲染进程的 12% 完全来自隐藏的主窗口：`window.hide()` 之后 WebView 仍认为自己可见，循环动画和每秒 12 次的电平更新照常渲染。GPU 进程的 17% 同时包含可见字幕窗的渲染，采样无法把两者拆开。现在主窗口隐藏期间暂停动画、不再应用电平，重新显示时恢复；改动后录音期间的占用需要真实录音才能采样，本次没有实测。

### 其余修复

- 操作提示固定写“按 Ctrl + Q”，与实际启用的触发方式无关。
- 最长录音看门狗线程每轮睡满 5 分钟才退出。按两个月的会话开始时间推算，同时存在的看门狗线程中位数 3 个、P90 为 7 个、最多 14 个。
- 安装版在没有统计文件时按工作目录新建；被开机自启动拉起时工作目录是系统目录，会一直写入失败。该问题对已有统计文件的用户不发生，属于条件性风险，按最小改动修复。

## 新增与变更

- 屏幕 OCR 首包等待超时后保留接收端，润色阶段取用已经到达的迟到结果，不做任何等待。最近 15 天约 7% 的会话 OCR 超时，其中触发润色的那部分此前拿不到屏幕参考。这是 0.13.0 审计里记录的后续项。
- 开机自启动（注册表启动项带 `--autostart`）且语音识别已配置好时主窗口保持隐藏；手动打开或尚未配置好时仍然显示。从托盘“重启程序”和托盘图标创建失败这两种情况也照常显示，保证始终有入口。没有新增配置项。
- 移除 `tray.show_startup_message` 与 `tray.startup_message_timeout_ms`：对应的启动提示窗自早期稳定性修复起就不再创建，开关没有任何效果。同时删除前端残留的 toast 模式、组件、样式和文案。

## 被实测否定的优化方向

| 方向 | 实测 | 结论 |
| --- | --- | --- |
| 缩短屏幕 OCR 固定开销以降低超时率 | 4K 下截图 66-130ms、识别 130-230ms；可去掉的开销（复用引擎、DIB section、直接写位图缓冲）合计 10-15ms | 不到总耗时 4%，不值得改动两段 unsafe 代码 |
| LLM 连接复用或录音开始时预热 | 握手约 40-45ms，复用只快约 45ms；服务端 30-60 秒回收空闲连接，仅 17% 的润色请求距上一次不足 60 秒 | 收益太小，且要把每会话一个的运行时改成全局共享 |
| 优化每次输出后整读统计文件 | 24476 条记录整读约 12ms，发生在粘贴之后 | 用户无感，暂不处理 |

明细记入 `docs/asr-quality-latency-guardrails.md`。

## 主链路影响

- 触碰主链路的改动只有剪贴板输出（打开方式、读回重试、快照判定）和润色参考信息的来源（迟到 OCR）。
- 未修改：音频分片与发包节奏、最终包门禁、`definite=true` 分句选择、空识别失败态、停录尾音窗口、润色触发条件、热键与输入钩子、统计内容。
- 粘贴时机：粘贴延迟现在从文本写入剪贴板那一刻算起。无冲突时与此前相差一次读回的耗时（亚毫秒级）；有冲突时读回重试的时间计入延迟而不是叠加在后面。
- 不可破坏规则核对：写入剪贴板失败仍返回错误并走既有兜底提示；悬浮字幕没有新增瞬时状态；统计仍不含正文；新增日志只有计数、耗时和启动方式名称。

## 配置、界面与文档

- 配置：移除两个无效字段，同步 Rust 模型、配置模板、前端默认值与类型；旧配置含这两个字段时照常加载，有回归测试。

## 独立复审

本次改动涉及剪贴板这类外部写入和启动流程，按协作规则对 `origin/main...HEAD` 的差异和直接调用链做了一轮独立的只读复审（不运行构建和测试，只读代码与依赖源码），发现逐条核实后处理。结论是没有发现会破坏主链路的问题；确认的问题都是低级别，处置如下：

| 发现 | 处置 |
| --- | --- |
| 首屏加载期间到达的主窗口显示事件，会被稍后返回的旧快照盖回“隐藏”。自启动隐藏后立刻从托盘打开时，窗口可见但动画和电平条停住 | 已修复：记录事件次数，快照在路上时来过事件就不采用快照里的可见性 |
| 托盘“重启程序”会把 `--autostart` 原样带给新进程，重启后主窗口不显示 | 已修复：重启前设环境变量，新进程照常显示主窗口；有单测 |
| 自启动隐藏时如果托盘图标创建失败，应用没有任何界面入口 | 已修复：此时显示主窗口。任务栏尚未就绪不属于这种情况，托盘库会在任务栏创建后重新注册 |
| “屏幕 OCR 迟到结果已用于润色参考”在不润色的会话里也会记录 | 已修复：只在确实要润色时取用并记录 |
| 两条真实剪贴板手工回归按注释里的命令会并行运行，互相覆盖并可能丢失原剪贴板 | 已修复：共用一把锁；用守卫保证断言失败时也恢复原内容；命令补上 `--test-threads=1` |
| 主窗口页面也在处理字幕事件，隐藏时仍对每条实时字幕做排版测量（非本次引入） | 已修复：只有字幕页处理 |
| “此前会把数据转换两遍”的说法没有实测依据 | 已改为只陈述事实：每个格式少取一次 |
| 位图族按双向合成判定：来源程序同时放了 `CF_DIB` 和带透明通道的 `CF_DIBV5`、而后者因额度被跳过时，恢复后透明通道丢失却不计入丢失 | 已接受差异：API 分不出一份 V5 是程序放的还是系统合成的，收紧会把截图场景的误报全部带回来；已写入代码注释 |

复审期间另行发现并处理：文本族合成判定原先是双向的，已收紧为只认“已备份 Unicode 文本”；Tauri 次版本升级会混进 Dependabot 常规分组，已单独成组。

## 已知差异与后续项

- 常用 4K 最大化窗口时，屏幕 OCR 仍有约 12% 赶不上 ASR 首包。可在 `config.toml` 把 `[screen_context].timeout_ms` 调到 `650-700` 换取更高命中率，代价是这部分会话的首条字幕最多晚一两百毫秒。默认值是否调整需要对首字体感的主观判断，本次不改。
- 主窗口和字幕窗各自加载完整前端。字幕窗只需要字幕和外观，启动时仍会执行完整的数据加载；拆分成独立轻量入口可以进一步降低内存，但属于较大的结构调整，本次不做。
- 0.13.1 运行 122 小时后两个渲染进程的私有内存分别为 466MB 和 286MB。本次去掉了隐藏期间的持续渲染和高频调用，是否因此不再增长需要新版本运行数日后复查。
- 关机或注销时 `tao` 偶发 panic `cannot move state from Destroyed`（两个月 8 次），发生在进程退出阶段，对使用无影响；属于上游问题，随 Tauri 升级再看。
- Tauri 2.12 升级留给单独的 PR。

## 手工回归建议

需要真实按键和麦克风，无法由 AI 自测：

1. 右 Alt 和 Ctrl + Q 各完成一次“说话 → 停止 → 粘贴”，确认文本正确、原剪贴板内容恢复。
2. 先复制一张截图，再语音输入一次，确认粘贴后截图仍可粘贴到画图或聊天窗口。
3. 远程桌面会话中语音输入几次，查看日志确认不再出现“剪贴板写入后读回失败”。
4. 主窗口收进托盘后录音，确认悬浮字幕和电平条正常；再从托盘打开主窗口，确认状态与动画恢复。录音时可顺便在任务管理器里看 VoxType 及其 WebView 进程的占用，补上本次没能实测的那一项。
5. 重启电脑，确认 VoxType 自动启动后只出现在托盘，点击托盘图标能打开主窗口。
6. 在托盘菜单点“重启程序”，确认重启后主窗口显示。

## 缺陷修复

`resize_to_ocr_limit` 在截图超过 Windows OCR 引擎 `MaxImageDimension`（通常 4096）时会缩放截图，原实现用最近邻取样。界面文字笔画通常只有一两个像素宽，最近邻会整笔丢弃，识别率明显下降。

同一张截图实测：

| 长边上限 | 实际画幅 | OCR 耗时 | 相对全幅词召回（最近邻 / 区域平均） |
| --- | --- | --- | --- |
| 不限 | 2194x1234 | 196-214ms | 100% |
| 2600 | 未触发缩放 | 177-186ms | 100% |
| 2000 | 2000x1125 | 180ms | 68.8% / 71.9% |
| 1600 | 1600x900 | 171-177ms | 58.6% / 69.3% |

改为逐目标像素对源区域取平均后，1600 档词召回从 58.6% 提升到 69.3%。该路径主要影响超宽屏或多显示器整屏截图的用户，他们此前一直在无感使用被劣化的 OCR 上下文；普通单屏用户不触发缩放，行为不变。

补两条单测锁住行为：`2x2` 缩到 `1x1` 必须得到四个源像素的平均值而不是某个角落像素；未超过上限时原样返回不复制。

## 被实测否定的优化方向

本轮原计划给截图加降采样上限以缩短首字延迟，实测后放弃：Windows OCR 耗时由固定开销和文本区域数主导，不随像素数线性下降，长边缩到 1600 只省约 17% 时间，却要赔掉三成以上的词。该结论与上表一并记入 `docs/asr-quality-latency-guardrails.md`，并在"不应回退的做法"中明确写入，避免以后再往这个方向优化。

真实使用日志同时显示，`500ms` 等待上限的命中率已达 20/22，继续降低跳过率应优先缩小 `capture_scope` 范围，而不是缩小分辨率。

## 审计核对通过、无需改动的项

- 配置模板、Rust `AppConfig::default()`、前端 `fallbackConfig` 三者无字段与默认值漂移。比对用 Rust 自身序列化的默认值，差异仅为 `Option` 字段在 `None` 时被跳过序列化。
- 生产代码只有 1 处 `expect`（`OwnedGlobalMemory::handle`），由类型结构保证不会触发：`transfer_to_clipboard` 消费 `self`，转移后对象不可再用。
- `unsafe` 块全部为 Win32 FFI，集中在 `hotkey.rs`、`text_output.rs`、`screen_context.rs`、`system_audio.rs`、`overlay.rs`。
- 统计只写时间戳、时长和字数；日志调用中没有密钥或识别正文。`console_api_key` 因字段名包含 `api_key` 子串被现有键值脱敏规则覆盖，已补回归测试。
- 仓库内 Markdown 无失效相对链接（`docs/wiki/` 内为 GitHub Wiki 语法，不是仓库路径）；代码中无 TODO/FIXME 遗留。
